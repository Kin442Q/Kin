## A. Демо-режим («живое демо» для лендинга)

Изолированное учреждение-витрина: любой посетитель лендинга входит одним кликом и **только
смотрит** реальные экраны на правдоподобных данных. Любые мутации заблокированы на уровне guard.

### A.1 Модель данных — *дополняет §6.2 (Kindergarten)*
Новое поле:
```
isDemo  Boolean  @default(false)
```
Демо-учреждение помечается `isDemo=true`. Миграция: `20260609130000_add_demo_flag`.
Остальные поля и каскады — без изменений.

### A.2 Токен и req.user — *дополняет §4 (Access JWT) и §5*
- В **access-payload** добавлено поле `isDemo: boolean`. Итоговый payload:
  ```ts
  { sub, email, role, kindergartenId|null, groupId|null, childId|null, isDemo, jti }
  ```
- `isDemo` вычисляется **на каждом выпуске токена** (`issueTokens`) по учреждению пользователя:
  смотрится `Kindergarten.isDemo` для `user.kindergartenId`. Значит, флаг = `true` для **любого**
  входа в демо-учреждение (в т.ч. обычный `/login` демо-админом), а не только через `demo-login`.
- JWT-стратегия кладёт `isDemo` (default `false`) в `req.user` (тип `AuthUser`).
- Refresh-payload **не меняется**: `{ sub, jti }`.

### A.3 Эндпоинт — *дополняет таблицу эндпоинтов §4 (auth)*
| Метод | Путь | Доступ | Поведение |
|------|------|--------|-----------|
| POST | `/auth/demo-login` | **Public** | Вход в «живое демо». Тело не требуется. HTTP 200. Ставит refresh-cookie, возвращает `{ user, accessToken }` (та же сериализация user, что и в §4). |

Логика выбора:
1. Найти учреждение: первое `Kindergarten` с `isDemo=true AND isActive=true`, сортировка
   `createdAt asc`. Нет → `404` «Демо-учреждение не настроено».
2. Найти пользователя в этом учреждении в порядке предпочтения: `role=ADMIN` →
   иначе `role=TEACHER` → иначе любой `isActive=true`. Нет → `404` «В демо-учреждении нет пользователя».
3. Выпустить пару токенов для найденного пользователя (как при обычном логине; `isDemo=true`
   попадёт в access-token по правилу A.2). `lastLoginAt` здесь **не** обновляется.

### A.4 Guard read-only — *дополняет §5 (Гварды)*
`DemoReadOnlyGuard` — **глобальный** guard (`APP_GUARD`), регистрируется **сразу после**
`JwtAuthGuard` и **до** `ThrottlerGuard`. Порядок глобальных провайдеров:
```
JwtAuthGuard → DemoReadOnlyGuard → ThrottlerGuard → LoggingInterceptor
```
Правила (`canActivate`):
- Если `req.user.isDemo` отсутствует/`false` → пропустить (для не-демо ничего не меняется).
- Метод `GET`/`HEAD`/`OPTIONS` → разрешить.
- Путь содержит `/auth/` → разрешить (демо-пользователь может `logout`/`refresh`).
- Иначе (`POST`/`PUT`/`PATCH`/`DELETE` на доменные ресурсы) → `403 Forbidden`,
  сообщение: `Демо-режим: изменение данных отключено. Зарегистрируйтесь для полного доступа.`

> При портировании: guard должен видеть уже распарсенного пользователя (выполняться после
> аутентификации) и опираться на флаг `isDemo` **из токена**, не ходя в БД.

### A.5 Сид демо — *дополняет §16 (Сиды/демо)*
Скрипт `npm run seed:demo` (`tsx prisma/seed-demo.ts`). **Идемпотентен и служит сбросом:**
при запуске удаляет прежний демо-тенант по `slug='demo'` (каскадно) и создаёт заново.
Создаёт изолированное учреждение **типа `SCHOOL`** `isDemo=true` (`slug='demo'`, «Демо-школа
«Maktab»») и наполняет:
- 3 класса (5 А / 5 Б / 11 Г), `capacity=30`, `fixedMonthlyExpense=8000`, индивидуальные `monthlyFee`;
- пользователи: `demo-admin@maktab.tj` (ADMIN) и `demo-teacher@maktab.tj` (TEACHER, ведёт все 3
  класса через M:N), пароль обоих — `Demo123456!`;
- 5 предметов; 4 четверти (`QUARTER`) относительно «сегодня» (третья — текущая);
- по 8 учеников на класс + оплата за текущий месяц (часть `paid`);
- расписание (4 урока × будни на класс); оценки и посещаемость за текущую четверть;
- несколько расходов (SALARIES/UTILITIES/FOOD) для финансовой аналитики.

Детерминированный ГПСЧ (seed=7) — данные стабильны между прогонами.

## B. Восстановление пароля через администратора — *дополняет таблицу §4 (auth)*

Email/SMS-инфраструктуры нет (см. §13 — каналы EMAIL/SMS не подключены), доступ выдаёт админ,
поэтому self-service сброса по ссылке **нет**: запрос лишь уведомляет администратора.

| Метод | Путь | Доступ | Поведение |
|------|------|--------|-----------|
| POST | `/auth/forgot-password` | **Public** | `{ email?, phone? }` (одно из). HTTP 200. |

Логика (`requestPasswordReset`):
1. Нормализовать: `email` → lowercase+trim, `phone` → trim. Если оба пусты → вернуть generic-ответ.
2. Найти пользователя: по `email` (`findUnique`) или по `phone` (`findFirst`). Не найден или
   `isActive=false` → вернуть generic-ответ (**не раскрывать существование аккаунта**).
3. Определить получателей-админов:
   - если у пользователя есть `kindergartenId` → активные `ADMIN`/`SUPER_ADMIN` этого учреждения
     **плюс** глобальные `SUPER_ADMIN` (`kindergartenId=null`);
   - если `kindergartenId=null` → все активные `SUPER_ADMIN`;
   - из выборки исключается сам инициатор (`id != user.id`).
4. Каждому админу создать **in-app** `Notification`: title «Запрос на сброс пароля»,
   description — ФИО + контакт (email/phone) инициатора + «Сбросьте пароль в карточке пользователя».
5. **Ответ всегда одинаковый** (независимо от шагов 2–4):
   `{ ok: true, message: 'Если аккаунт найден, администратор получит запрос и сбросит пароль.' }`.
6. Метод обёрнут в try/catch — наружу не бросает, при любой ошибке отдаёт тот же generic-ответ.

Сам сброс пароля делает админ существующим механизмом обновления пользователя
(`PATCH /users/teacher/:id` с `password`, и т.п. — см. §8 users; bcrypt cost=10).

> Уведомление администраторам идёт каналом `IN_APP` (см. §6.2 Notification, §8 notifications).
> Telegram/Push здесь не задействованы.

## C. Доступ учителя к расписанию и собраниям — *изменяет §5, §8 (schedule, meetings), §9.7*

Ранее учитель в расписании/собраниях был ограничен **основной** группой (`user.groupId`) и не
мог редактировать расписание. Теперь и там, и там действует общий набор «своих классов»
`teacherGroupIds = Set(groupId + teachingGroups[].id)` (как в §5), и учителю выдан **write**-доступ
к расписанию своих классов.

### C.1 Schedule `/schedule`
- **GET `/`** — TEACHER видит расписание **всех своих классов** (`teacherGroupIds`), а не только
  основного. Если передан `groupId` и он входит в свои классы — вернуть только его; иначе — все
  свои. Нет классов → `[]`. Для не-TEACHER фильтр по `groupId` как прежде; всё ограничено
  `kindergartenId` пользователя.
- **POST `/` / PATCH `/:id` / DELETE `/:id`** — роли теперь **`SUPER_ADMIN, ADMIN, TEACHER`**
  (ранее только SA/ADMIN). TEACHER может менять расписание **только своих классов**
  (`groupId ∈ teacherGroupIds`), иначе `403`. Тенант-проверка (`kindergartenId`) сохраняется.

### C.2 Meetings `/meetings`
- **GET `/`** — TEACHER видит собрания **всех своих классов** (`teacherGroupIds`). Если передан
  свой `groupId` — только он; иначе — все свои; нет классов → `[]`.
- **POST `/` / PATCH `/:id` / DELETE `/:id`** — роли без изменений (SA, A, T), но проверка
  принадлежности у TEACHER теперь по `teacherGroupIds`, а не по единственному `user.groupId`
  (создавать/менять/удалять можно для любого своего класса). Иначе `403`.

### C.3 Сводная правка матрицы §5
TEACHER:
- **Расписание** — было «(чтение)»; стало «чтение **и запись** для своих классов».
- **Собрания** — область «своя группа» расширена до «все свои классы».

## D. Обновления контрольного списка §17 (acceptance)

Дополнительно к пунктам 1–10 основного ТЗ проверять:
11. `demo-login` отдаёт рабочую сессию; `isDemo=true` присутствует в access-токене для демо-тенанта.
12. `DemoReadOnlyGuard`: для демо-пользователя все мутации (`POST/PUT/PATCH/DELETE`) вне `/auth/*`
    → `403`; `GET` и `/auth/*` — проходят.
13. `seed:demo` идемпотентно пересоздаёт тенант `slug='demo'`.
14. `forgot-password`: одинаковый generic-ответ при найденном/ненайденном аккаунте; админам
    создаётся in-app уведомление; эндпоинт не бросает наружу.
15. Учитель: чтение расписания и собраний по **всем своим классам**; запись расписания только
    для своих классов; чужой класс → `403`.
